# ShabCRM

- Package manager: pnpm. Check with `pnpm lint && pnpm typecheck && pnpm test`; browser flow with `pnpm build && pnpm test:e2e`.
- Tenant data (contacts, activities, pipelines, pipeline_stages, deals, messages, calendars, appointments, workflows, workflow_runs, workflow_run_logs, form_submissions) must be read and written inside `withWorkspace()` from `src/db/tenant.ts`. Outside it, row-level security only protects you if the database user isn't a superuser, and hosted Postgres usually is.
- Pages and server actions call `requireWorkspace(id)` from `src/lib/session.ts` before touching a workspace.
- Business logic lives in `src/server/*` and takes `db` as a parameter so it can be tested in `tests/` against a real Postgres.
- Forms use `useActionForm` (`src/components/use-action-form.ts`) so typed input survives validation errors.
- SMS consent rules: never upgrade a contact whose consent is `revoked` (the one exception is the contact texting START themselves); granting consent always records a source. Texting without consent is only allowed within 24 hours of the contact texting or calling in (`textPermission` in `src/server/messaging`).
- Messaging goes through the provider interfaces in `src/server/messaging/providers.ts`: text and WhatsApp (Twilio), iMessage (Sendblue), email (Postmark). With a service's keys unset, test providers record messages without sending. Webhooks must verify the Twilio signature, the Postmark secret, or the Sendblue secret (status callbacks: the `statusToken` in their URL) before doing anything.
- iMessage shares text consent (STOP/START, the 24-hour reply window). WhatsApp has no stored consent: it's allowed only within 24 hours of the contact's last WhatsApp message (`whatsappPermission`). Inbound text, iMessage and WhatsApp all fire `sms_received`.
- `booking_pages` and `forms`, like `workspaces`, are read without row-level security because public pages look them up by slug (`forms` has RLS enabled but not forced, so edits inside `withWorkspace()` stay isolated); keep anything private out of them. Calendar credentials are encrypted with `encryptJson` (`src/server/calendars/secrets.ts`).
- Website form capture (`src/server/form-capture.ts`, `/api/capture/[key]`): `workspaces.capture_key` is public (it's in the snippet on client sites), so the endpoint only ever adds submissions; it never reads data back. Captured forms are `forms` rows with `source = 'website'` and never set SMS consent.
- Sidebar counts (`src/server/badges.ts`, polled from `/api/badges`): each person's `user_prefs.clear_per_item` picks clearing item by item (`markItemsSeen`/`markContactSeen` from the pages and actions that open or act on an item) or by tab (`markTabSeen` when a tab page renders). `tab_seen`, `item_seen` and `user_prefs` are per person, like `todos`, read by user id outside `withWorkspace()`; the counts are read inside it, so `item_seen` is granted SELECT to `shab_app`.
- Outside calendars go through the `CalendarProvider` interface (`src/server/calendars/providers.ts`); data functions take a `ProviderFactory` so tests can pass fakes.
- Workflows (`src/server/workflows`): changes that should start a workflow call `fireTrigger(tx, …)` inside the same transaction. The background worker (`src/instrumentation.ts`) claims due runs from `workflow_queue`, which has row-level security enabled but not forced so the worker can see every account's due runs; everything else about a run is read inside `withWorkspace()`. A run moves its pointer past a step before doing it, so a crash never sends a text twice. Builder labels live in `src/lib/workflows.ts`.
- AI (`src/server/ai`): each account connects its own model in `ai_settings` (key encrypted with `encryptJson`; `getAiSettings` never returns it). `makeLlm` (`src/server/ai/llm.ts`) wraps Claude via `@anthropic-ai/sdk`, and OpenAI, Gemini and OpenAI-compatible services over HTTP; data functions take an `Llm` or `MakeLlm` so tests pass fakes. The AI only drafts and tags; it never sends. Inbound messages are queued in `ai_queue` (RLS enabled, not forced, like `workflow_queue`) and tagged by the worker, which fires `intent_detected`. Intent labels live in `src/lib/ai.ts`.
- Speed-to-lead alerts (`src/server/lead-alerts.ts`, run by the worker every minute): `workspaces.lead_alert_*` settings; only a person's reply (`messages.created_by` set) counts as answered; `lead_alerted_at` on messages and form submissions is set before sending so an alert never goes twice.
